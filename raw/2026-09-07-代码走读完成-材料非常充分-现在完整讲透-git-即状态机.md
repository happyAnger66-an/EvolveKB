# AKA 的“Git 即状态机”（代码级剖析）

## 核心思想：状态分两类，各有各的存储

AKA 把所有状态切成**两个世界**，这是理解整个设计的钥匙：

| | 权威状态（Git 提交的） | 运行时状态（磁盘上、gitignore 的） |
|---|---|---|
| **内容** | kernel.py + memory/vN.json + memory/eNNNN.json | state.json / live.json / stall / journal / handoff / plans |
| **谁写** | 只能 supervisor（`--only` 白名单提交） | Agent 和 supervisor 都写 |
| **作用** | **“什么是现任最优”的唯一事实** | 进度追踪、崩溃恢复的线索 |
| **丢失后果** | 不可丢（Git 对象库保护） | 可丢——**丢了能从 Git 重建** |

实跑验证（我 4090 复现的目录树）：
```
Git 提交的（git ls-tree HEAD）:
  kernel.py                    ← 现任最优 kernel 本体
  memory/v0.json, v1.json      ← 每个版本的测量记录（延迟/score/improvement_pct）
  memory/long_horizon_e0001.json ← episode 证据（5 个 trial 的完整记录）
  definition.json / test_kernel.py / ... ← 不可变的 ground truth

磁盘上但不进 Git:
  .atrex_long_horizon/state.json     ← supervisor 计数器（episodes/accepted/tokens）
  .atrex_long_horizon/live.json      ← 活动 episode 的 best-effort 进度
  .orchestrator_state.json           ← stall 计数器
  .atrex_long_horizon/episodes/e0001/ ← 归档（journal/handoff/plans/telemetry）
```

## 状态机的“状态”是什么：phase 字段

`SupervisorState`（`long_horizon/models.py:92`）是计数器层：
```python
class SupervisorState:
    episodes: int = 0        # 跑了几个 episode
    accepted: int = 0        # 晋升了几个
    rejected / pivoted / blocked / interrupted / protocol_failures: int
    tokens: int = 0          # token 预算消耗
    consecutive_without_promotion: int = 0   # ← stall 检测的输入
```

而**真正的状态机转移**是 `active["phase"]` 字段（`campaign.py`），生命周期：

```
preparing → exploring → checking_fast_evaluator/verifying → promoting → promoted → recording → recorded
```

每次 phase 变化都**先写盘再行动**（`store.save_active(active)`）——这就是“崩溃后能恢复”的秘密：phase 落在磁盘上，进程死了 phase 还在。

## HEAD = incumbent：一个不变量，三种用途

**不变量：incumbent 仓库的 HEAD 永远指向“经过验证的现任最优 kernel”**。这个不变量支撑了三件事：

### 用途 1：晋升时的并发检查
```python
# promote_candidate() 第一行
if git_head(incumbent_workspace) != base_commit:
    raise RuntimeError("incumbent advanced during episode; refusing promotion")
```
episode 开始时记下 base_commit，晋升时如果 HEAD 变了（另一个 episode 并发晋升过），**拒绝晋升**而不是盲目覆盖。Git 的 commit hash 天然做了乐观锁。

### 用途 2：stall 检测的“真伪赢”判断
```python
def commit_changed_kernel(workspace, ref) -> bool:
    # git show --numstat <commit> -- kernel.py
    # 只有真正改了 kernel.py 的提交才算"赢"
```
stall 计数器数的是“从 HEAD 往回，连续多少个提交**没改 kernel.py**”。注意这个设计的巧妙之处：**失败也提交**（作为证据），所以不能数“提交数”来判断停滞——必须数“改了 kernel.py 的提交”。而“改没改”由 Git 的 numstat 客观回答，不依赖任何自报状态。

版本号不是存在某个变量里，而是**从 Git 提交的文件名集合推导**。没有“版本计数器丢失”这回事——文件在版本就在。甚至处理了边界：`v71_512.json`（实验分支的 scratch 文件）不能被 Python 的 `int('71_512')==71512` 误判成 v71512，用严格正则排除。

## 崩溃恢复：三级递进

这是“Git 即状态机”最出彩的部分。进程随时可能死（OOM、断电、Ctrl-C），恢复逻辑分三级：

### 第一级：phase 恢复（supervisor 自己死）
```python
resumable_worktree = bool(
    git_head(self.workspace) == base_commit          # incumbent 没被动过
    and phase in {"preparing","exploring","verifying","promoting","recording"}
    and worktree_path in registered_worktrees          # worktree 还在 git worktree list 里
    and branch 存在 and base_commit 是 HEAD 祖先       # 分支历史完整
)
```
重启后读 state.json 的 phase，**从断点继续而不是重跑**：
- `exploring` 死的 → 重新拉起 Agent 会话（worktree 里的 Git 提交还在，Agent 从 journal 接力）
- `promoting` 死的 → 检查 incumbent 是否有半完成的 squash（`working_changes`），有则 `git reset --hard base_commit` 回滚后重试晋升
- `recording` 死的 → 检查 memory 文件是否已提交（`outcome_recorded`），是则跳过

**关键：所有“做到哪了”的判断都用 Git 原语回答**（HEAD 是什么、worktree 列表里有没有、merge-base 是不是祖先），不信任任何自报状态。

### 第二级：Agent 接力（Agent 死，supervisor 活着）
Agent 会话崩溃时，`handoff_resumes=2` 允许同线程重试。接力靠两个文件：
- **journal.json**：Agent 每个 trial 追加一条实验记录（hypothesis/change/result/decision）
- **handoff.json**：Agent 的终端交接（实跑产物就两行：`{"status": "candidate_ready", "candidate_commit": "79caa3b..."}`）

新 Agent 会话起来后读 journal 知道前 3 个 trial 试过什么，从 handoff 知道是否已有结论。**Agent 的记忆外置到文件，会话本身无状态**。

### 第三级：环境恢复（GPU 机器挂了）
远端 GPU 健康探测失败 → supervisor 停止、保留 worktree、生成两个脚本：
```bash
recover.sh        # 服务器恢复后手动执行 → 重启原 campaign 命令
stop-recovery.sh  # 停掉自动恢复监控
```
外加一个 detached monitor 进程轮询 GPU 健康，恢复后自动 resume。设计上很谨慎：**自动恢复默认保守**（意外退出回到轮询，只有“干净退出零”才算恢复完成），防止恢复逻辑本身造成重复执行。

## 原子性：durable_write 的偏执

所有状态写入走 `durable_write_text`（`orchestrator/durable_state.py`）：

```python
def durable_write_text(path, value):
    temporary = f".{path.name}.{os.getpid()}.{uuid4().tmp}"   # 临时文件
    fd = os.open(temporary, O_WRONLY|O_CREAT|O_EXCL, 0o600)   # 独占创建
    stream.write(value); stream.flush()
    os.fsync(stream.fileno())          # ← 数据落盘
    os.replace(temporary, path)        # ← 原子改名
    fsync_directory(path.parent)       # ← 目录项也落盘
```

三重保障：临时文件+原子 rename（读者永远看到完整文件）、fsync 文件（防掉电丢数据）、**fsync 目录**（防 rename 本身丢失——大多数人漏掉这步）。状态文件损坏 = 状态机失忆，所以这里值得偏执。

## 实跑验证：状态机的完整轨迹

我 4090 复现留下的状态链（可完整回放）：

```
Git 历史（权威）:
  b92fb3d  V0: baseline (SOL reference wrapper)        ← supervisor
  d4ad316  V0: record baseline measurement             ← supervisor (memory/v0.json)
  b3c8225  episode 1: promote verified candidate       ← supervisor (kernel.py + v1.json + e0001.json)

state.json（运行时）:
  accepted: 1, episodes: 1, tokens: 8382850
  attempts[0]: {base_commit: d4ad316, candidate_commit: 79caa3b,
                promotion_commit: b3c8225, status: candidate_ready, ...}

live.json（进度快照）:
  version: v1, phase: recorded, journal_state: candidate_ready
  latest_experiment: {trial 5 的完整记录, decision: reject_and_continue}
```

注意 `attempts[0]` 里存了**三个 commit hash 的链条**：base（从哪出发）→ candidate（Agent 的最优）→ promotion（squash 后的新 HEAD）。任何一个环节都能用 Git 命令独立验证——这就是“状态机”的含义：**每个转移都有不可篡改的落点，且落点之间由 Git 的 DAG 结构保证一致性**。

## 设计洞察：为什么用 Git 而不是数据库

对比一个假设的“用 SQLite 存状态”方案：

| 需求 | SQLite | AKA 的 Git 方案 |
|---|---|---|
| incumbent 是什么 | 查表 | `git HEAD` + blob 内容 |
| 崩溃后知道做到哪 | WAL 回放 | phase 文件 + Git 原语探测 |
| 防并发晋升 | 事务锁 | commit hash 乐观锁 |
| 历史可审计 | 需要额外设计 | `git log` 天然免费 |
| 与代码变更绑定 | 需要外键 | **状态和它描述的代码在同一个提交里** |

最后一行是本质：**v1.json（测量记录）和 kernel.py（被测代码）在同一个 commit 里**——你不可能拿到“记录说 1.36x 但代码其实是另一份”的状态。状态与事实的原子绑定，数据库做不到，Git commit 天然做到。

**一句话总结**：AKA 把 Git 当成了一个自带持久化、并发控制、历史审计的分布式状态机——HEAD 是状态，commit 是转移函数， worktree 是并发分支，gitignore 的运行时文件只是缓存（可从 Git 重建）。所有“做到哪了”的终极裁判都是 Git 原语，而不是任何自报数据。
