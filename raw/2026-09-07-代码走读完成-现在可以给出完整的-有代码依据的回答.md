# AKA 权责边界的实现机制（代码级）

AKA 的权责边界不是一句设计原则，而是**六层独立机制叠加**，每层防不同的越权路径。我按“Agent 想干什么坏事 → 哪层拦住它”来组织：

## 第 1 层：文件系统隔离（Agent 只能碰自己的 worktree）

**实现**（`long_horizon/git_episode.py` `EpisodeWorktree.plan/materialize`）：
```python
# 每个 episode 一个独立 worktree + 独立分支
branch = f"atrex/long-e{episode:04d}-{uuid.uuid4().hex[:8]}"
path = worktree_root / f"e{episode:04d}-{uuid.uuid4().hex[:8]}"
# materialize: git worktree add -b <branch> <path> <base_commit>
```

**会话进程的 cwd 就是这个 worktree**（`long_horizon/campaign.py:2008` → `session.py:203`）：
```python
result = runner.run(worktree.path, prompt, ...)  # 第一个参数 = cwd
# session.py: self.executor(command, workspace, None, environment)  # workspace=worktree.path
```

Claude 进程从启动就在 `e0001-xxxx/` 目录里，incumbent 主仓在另一个路径。**Agent 想改 incumbent 得先知道路径再主动 cd 过去**——prompt 明令禁止，且即使它这么做了，还有后面几层。

## 第 2 层：Prompt 契约（软约束，但写得很硬）

实际下发给 Claude 的 `fast_episode.md` 模板（我实跑时抓到的完整 prompt）：

> *"The supervisor owns the incumbent branch, canonical memory, acceptance, and squash promotion. You own only this episode branch, its final `kernel.py`, journal, and terminal handoff."*
>
> *"Never switch branches, push, merge, rebase, or alter refs. **Every commit must contain only `kernel.py`**. Plans, journals, and handoffs are ignored episode evidence and must never be added to Git. Never edit evaluator or ground-truth files, including `test_kernel.py`, `profile_driver.py`, `definition.json`, `reference.py`, `workload.jsonl`... Do not write canonical `memory/vN.json`; the supervisor writes and commits one for every terminal episode."*

注意它约束的粒度：不只是“别干坏事”，而是**精确到文件名**——哪些文件你能改（只有 kernel.py），哪些绝对不能碰（列举了 10+ 个），哪些是“你能写但不会进 Git”（journal/plans/handoff）。

## 第 3 层：Git 排除规则（证据文件物理上进不了提交）

`long_horizon/store.py` `CampaignStore.ensure_excluded()`：每个 worktree 创建时自动往 `.git/info/exclude` 写入：

```python
rules = (
    f"/{RUNTIME_DIR}/",      # .atrex_long_horizon/
    f"/{VERIFY_DIR}/",       # eval/
    "/plans/",               # Agent 的计划文件
    "/profiles/",
    "/.humanize/",
)
```

效果：即使 Agent 违反 prompt 执行了 `git add plans/`，这些路径**被 Git 物理忽略**，不可能进入候选提交。这是“prompt 说了不算，Git 说了算”的第一道硬保障。

## 第 4 层：晋升时的保护路径检查（supervisor 侧，Agent 绕不过）

这是**最关键的一层**。Agent 的分支最终要被 supervisor squash-promote 到 incumbent，`promote_candidate()`（`git_episode.py:269`）在合并时做三重检查：

```python
def promote_candidate(...):
    # 检查 1: incumbent 没被并发修改
    if git_head(incumbent_workspace) != base_commit:
        raise RuntimeError("incumbent advanced during episode; refusing promotion")

    # 检查 2: squash 后逐文件检查保护路径
    git merge --squash --no-commit <candidate_commit>
    staged = git diff --cached --name-only
    violation = protected_violation(staged)   # ← 这里
    if violation:
        raise RuntimeError(violation)

    # 检查 3: 只提交白名单文件(--only 精确指定)
    git commit --only -m "..." -- kernel.py memory/e0001.json memory/v1.json
```

`protected_violation` 检查的完整黑名单（`git_episode.py:15-40`）：

```python
PROTECTED_PATHS = frozenset({
    "test_kernel.py", "profile_driver.py", "definition.json",
    "reference.py", "workload.jsonl", "input.py", "agent_problem.json",
    "shapes.json", "metadata.json", "roofline.json", "valid.py",
    "CLAUDE.md", "README.md", ".gitignore",
})
PROTECTED_PREFIXES = ("memory/", "eval/", ".claude/", ".qoder/", ".agents/", ".atrex_")
```

**关键设计**：这个检查在 supervisor 进程里跑，Agent 无法修改 supervisor 代码（它只能碰自己的 worktree）。即使 Agent 在自己分支上改了 `test_kernel.py`（作弊让评测变简单），squash 时会被 `protected_violation` 拦下，整个晋升失败。

## 第 5 层：进程守卫（实时监控 Agent 的子进程树）

`orchestrator/agent_runtime/process.py` 的守卫线程——这是最“较真”的一层。Claude 会话启动后，一个**独立线程每秒轮询 `/proc`**，遍历 Agent 所有后代进程的 cmdline：

```python
# 守卫线程: while not stop.wait(POLL_SECONDS):
for pid, argv in descendant_process_commands(proc.pid):
    reason = dependency_process_violation(argv)
    if reason:
        violations.append(f"pid={pid}: {reason}")
        signal_process_groups(descendant_process_groups(proc.pid), SIGTERM)
        # 1秒不退就 SIGKILL 整个进程组
```

拦截的命令黑名单（`is_installer`，处理了各种绕过变体）：
- `pip install/wheel`、`python -m pip install`、`uv pip install/sync/compile`
- `conda/mamba install/create`
- `setup.py install/build/bdist_wheel`
- **甚至处理了 `python xxx.py -- pip install` 的 `--` 后缀形式**（防止借道脚本装包）
- 还会展开 `sh -c "..."` 的内嵌命令再检查

违规后果：**整个 coding session 被杀**（exit code 126），不只是那条命令失败。理由在 prompt 里也写了：预装依赖不可变，防止 Agent 通过装包改变评测环境。

## 第 6 层：验证器不信工作区文件（防“评测时换文件”）

晋升前的 ABBA 验证（`long_horizon/verifier.py`）有个容易忽略的细节：**它不从工作区读 kernel.py，而是从 Git blob 读**：

```python
def _snapshot_revision(workspace, revision, changed_paths, ...):
    content = _git_blob(workspace, revision, relative)  # git show <commit>:<path>
```

也就是说：Agent 提交了 commit A（评测通过），然后偷偷改工作区的 kernel.py（未提交）——验证器拿到的还是 **commit A 的字节**。评测的对象和晋升的对象是同一份字节，杜绝了“评测时用一个文件、合入时是另一个文件”的时序攻击。

ABBA 调度本身（`verification_schedule`）也值得注意：
```python
# repeat 0: incumbent → candidate
# repeat 1: candidate → incumbent   (顺序交替，消除 GPU 状态/温度漂移)
```
同一 GPU 分配内交替跑两版，取几何均值比较——测量噪声的控制做到了对照组级别。

## 总结：为什么这套设计有效

| 越权路径 | 拦截层 | 强度 |
|---|---|---|
| 改 incumbent 仓库 | L1 worktree 隔离 + L2 prompt | 物理+软 |
| 改 evaluator/ground truth | L4 protected_violation（晋升时） | **硬，不可绕** |
| 提交垃圾文件进候选 | L3 git exclude + L4 `--only` 白名单提交 | **硬** |
| 装包改变环境 | L5 /proc 守卫实时杀进程 | **硬** |
| 评测后偷换文件 | L6 从 git blob 取字节 | **硬** |
| 自我宣布“优化成功” | 无需拦截——晋升权根本不在 Agent 手里 | 结构性 |

**核心洞察**：AKA 没有试图让 Agent“变乖”（prompt 只是第一道便宜的防线），而是**假设 Agent 会越权，然后在每条越权路径上放一个 Agent 够不到的硬检查**。prompt 管“引导”，Git/supervisor/进程守卫管“强制”。软硬分层，且所有硬检查都在 Agent 的写权限之外——这是它能宣称“机械控制”的底气。

对比我们如果要做类似的事（比如 tirx-kernels 的 Agent 辅助优化）：最小可行版本是 L1（worktree）+ L4（晋升时 protected check + `--only` 提交）+ 我们已有的 cosine 门禁，三层就能覆盖 90% 的风险。L5 进程守卫是锦上添花，L6 git blob 取证在 evaluator 与提交解耦时才需要。
